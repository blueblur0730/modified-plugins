         * Windows verification target: engine.dll (PE32 x86, imagebase 0x10000000, PE timestamp 2026-06-30).
         * All three binary signatures below still match exactly once in that build
         * (RVA 0x12D750 / 0x4E870 / 0x4EC60) - see the per entry comments.
         *
         * Frame rule (Windows): MSVC puts the IClient subobject at +4 inside CGameClient /
         * CBaseClient / CHLTVClient (RTTI base class mdisp = 4), while the engine hands the auth
         * ticket helper the *complete* object pointer. Every IClient virtual therefore has to be
         * invoked on (client + 4):
         *     GetNetChannel = slot 18, GetClientName = slot 17, Disconnect = slot 13.
         * Direct (non virtual) calls into the engine's IClient implementations need the same +4 -
         * the Disconnect signature below *is* the IClient slot 13 implementation, and the engine's
         * own timeout check calls it as (client + 4)->vtbl[13]((client + 4), reason)
         * (CBaseServer::CheckTimeouts, engine.dll RVA 0x135880).
         */
        "Functions"
        {
            /*
             * The real function is
             *     void __thiscall CSteam3Server::OnValidateAuthTicketResponseHelper(CBaseClient *, EAuthSessionResponse)
             * i.e. TWO stack arguments (engine.dll: `retn 8`, verified in IDA).
             *
             * An earlier revision declared a phantom third argument ("a1"). DHooks builds its parameter
             * description from this list, so a third entry describes a frame one argument wider than the real
             * one - that is what made a SourcePawn Get(3) fail at runtime with
             * "Invalid param number 3 max params is 2" (observed live). The entry is removed because the
             * description has to match the function (retn 8, two stack arguments), NOT because a crash was
             * traced to it: a recorded Windows crash inside steam_api's callback pump was checked against that
             * theory and does not fit. Its five frames form an intact direct call chain (every recorded return
             * address lands exactly at call+5), the fault is a `mov eax, [esi]` pointer dereference in
             * steam_api's own container code, and no SourceMod / DHooks / engine frame appears in it at all.
             * A Supercede that had unbalanced the stack would have destroyed those return addresses.
             *
             * The plugin source has always used Get(1) = client and Get(2) = response, so dropping the phantom
             * argument needs no .sp change.
             */
            "CSteam3Server::OnValidateAuthTicketResponseHelper"
            {
                "signature" "CSteam3Server::OnValidateAuthTicketResponseHelper"
                "callconv"  "thiscall"
                "return"    "void"
                "this"      "ignore"
                "arguments"
                {
                    "CBaseClient"
                    {
                        "type"  "int"   // complete object pointer the engine passes (the helper adds +4 itself)
                    }

                    "EAuthSessionResponse"
                    {
                        "type"  "int"   // enum EAuthSessionResponse; the engine only calls this on non-zero (failure)
                    }
                }
            }
        }
